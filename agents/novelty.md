## Incremental discovery pass

The novelty channel plugin owns a fixed timer and sends notifications into this same foreground conversation. On a novelty tick, read new input and update local discoveries, then give a short report in the conversation and remain available to Alizain. Claude Code handles notifications that arrive while you are busy. Do not start /loop, an internal sleep loop, another scheduler or a second discovery worker. Do not choose a next-run time or return scheduling JSON. The timer runs while this foreground session runs; quitting Argo ends it. Opening the Claude tab does not trigger an immediate discovery pass.

Read new input from all seven sources: mail and calendars across the five configured accounts, CodeCreators Teams, Workflowy, Granola, WhatsApp, and the local Messages conversations exposed by imsg (iMessage and SMS). Determine the current UTC time at the start; that is this pass's upper input bound. Read data/novelty/progress.json before choosing lower bounds. Keep progress separately for each source/account so an unavailable source does not lose its unread interval. For a source/account with no progress, use the preceding seven days. Otherwise start at its last fully covered timestamp, including the boundary when the provider supports it, and inspect only the new interval. Existing doables are the shared record for recognizing work already discovered.

Own your discovery progress in data/novelty/progress.json. Record each source/account's covered-through UTC timestamp, the actual input bounds, brief coverage counts and any limitations. Advance its covered-through timestamp only after reading and evaluating that interval and persisting its discoveries. If reads are incomplete, retain its prior covered-through value (or leave it unset on first use) and record the actual gap; never claim coverage of skipped pages, blocked accounts or failed reads. This is small discovery bookkeeping, not a copy of source content. The earlier manual discovery conversation may provide context, but without saved per-source progress it does not establish a checkpoint.

Source pagination is part of a real pass. Examine input to distinguish actionable requests/commitments from newsletters, FYIs and already-completed work. Do not invent a quota. Do not pretend unvisited sources were checked. Use the actual sources directly, not a new source mirror. Do not write source content caches into the repo.

Use the installed Composio CLI and its working login. Known read operations and account selectors live in src/mail-service.ts, src/outlook.ts, src/calendar-service.ts, src/teams-service.ts and src/granola-service.ts. Inspect CLI schemas with composio execute SLUG --get-schema when necessary. For loops/parsing prefer composio run, whose execute and proxy are authenticated. Only GET for proxy. Output may be saved by the CLI into its own temp file; read that file. Use terminal scripts for transforming responses if needed, keep durable discovery output under data/ and use /tmp for temporary operational files. No separate project or authentication setup.

Mail: Gmail GMAIL_LIST_THREADS supports query, max_results and page_token, verbose true. Use after:<Unix-seconds> before:<Unix-seconds> for the input interval; date-only values mean midnight Pacific time and cannot represent incremental passes. Round the query's lower bound down with one second of overlap and its upper bound up, then evaluate message timestamps against the exact UTC input interval. Fetch detail where needed. Source references use Argo account ID and provider THREAD id (not message id). Outlook uses OUTLOOK_LIST_MESSAGES, filter receivedDateTime ge ..., allfolders, full; group by conversationId. For outlook references use conversationId.

Calendars: use the current source/account's input bounds with the service's existing reads. Google event references must reproduce Argo's ID `${accountId}:${source_calendar_id}:${event.id}` and month YYYY-MM of the event start. Outlook IDs are `${calendar.id}:${event.id}`. A scheduled meeting alone need not be a doable; infer work only from actual evidence.

Teams: use the account, user identity and read operations in src/teams-service.ts. Read recent messages in relevant recently active chats and paginate through the current input window. Context uses chatId.

Granola: use the account and read operations in src/granola-service.ts. List meetings in the current source/account's input range, then read summaries and relevant transcripts for commitments. Context uses meetingId.

Workflowy: use MCP tree_seek. It supports downward-deep from root with filter.modified_after or filter.created_after numeric timestamps and limits. Inspect the tool's schema for timestamp units; test the read filter using current timestamps if units are unclear, report any coverage uncertainty. Include recent nodes, including any #todo unconditionally, but do not sweep in old unfinished #todo nodes outside the current input window. If journal dates identify that window, read those branches. Context uses nodeId, the real source handle. Never use tree_patch, leases or any other mutation.

WhatsApp: use the existing whatsapp MCP read tools (list_chats, list_messages, get_chat, get_message_context). Inspect available arguments; filter after/before when provided and paginate. Preserve chat JID and optional messageId in references. Do not use send_message, send_file, download, mark_read, reactions, or any mutation.

iMessage: use the installed imsg CLI directly, matching src/imessage-service.ts. Read imsg chats --help and imsg history --help for the installed contract. JSON output is newline-delimited JSON, one object per line. Start with imsg chats --limit 100 --json; chats are ordered by recent activity. Increase the limit until the oldest returned chat predates the discovery window or fewer than the requested number return. For each chat active in the window, run imsg history --chat-id <id> --start <window-start-ISO8601> --end <window-end-ISO8601> --limit 100 --json. History is newest-first and applies its limit after the date filter. Increase the limit until fewer than requested return; do not mistake the default limit for complete coverage or use time-only pagination that drops tied timestamps. Read only the final expanded result once when evaluating obligations. References use source "imessage", a readable label, positive numeric chatId from the local database and optional messageId set to the observed message guid (not the numeric message row ID). Use resolved contact_name and sender_name where available; the source includes both iMessage and SMS, so retain the actual service rather than filtering to iMessage. Full Disk Access is needed for the responsible terminal/application, and Contacts access provides names. If those permissions block reading, report the actual gap; do not claim coverage or copy the Messages database elsewhere. Do not use send, react, watch, bridge, conversion/download, chat creation or mutation commands. This pass reads existing local data and never starts a background service.

## Output

Write one JSON file per worthwhile distinct doable at data/doables/<id>.json. Use a UUID for id. Required fields are id, title, description, rationale, status (initially "open"), context (nonempty array). Each context has source, label and fields exactly as src/doables.ts requires. Labels should be human-readable names/subjects. Description says what Alizain needs to do; rationale briefly explains the actual evidence and current apparent state. Keep concise enough to scan. Do not copy full threads or transcripts into a doable.

Read existing doables before creating; add relevant context to an existing doable rather than duplicate the same obligation. Do not mark any existing doable done or rejected in this pass. No children, stack order, deadlines, confidence scores or invented schema fields. Cross-source context belongs together when it is demonstrably the same obligation. Use only observed source IDs that Argo can open. Never invent names, IDs or evidence.

Before finishing, persist your progress and brief coverage/discovery counts, including created/updated file counts and any limits, in data/novelty/progress.json. Do not include private message bodies in this bookkeeping. The user will read the doables in Argo.

Report what you discovered, changed, or could not read in a brief conversational response. There is no scheduling result to return. The channel sends the next tick independently, and Argo observes the same local doable files you wrote. Do not refresh source caches or restart Argo.
